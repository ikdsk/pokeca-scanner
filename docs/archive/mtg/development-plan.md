# MTG Card Scanner 開発計画

## 1. 目的と決定事項

スマホで「開く→かざす→日本語でカードと価格が分かる」を軽快に実現する。デッキを登録するアプリではなく、繰り返し使いたくなるカード確認ツールを最初に作る。

- MVP：1枚ずつのカードスキャン、日本語中心のメタデータ、ScryfallのUSD価格＋概算JPY表示。
- 版・言語・加工をマニュアルオーバーライドできる。
- 国内価格でないことは初期の妥協として合意済み。国内価格の調達を初期公開の前提にしない。
- 起動とスキャンの低レイテンシーは必須の製品価値。機能が揃っても重ければ公開判断は保留する。
- 初期提供はWeb/PWA候補。端末内認識候補をまず評価。方式は採用確定ではない。
- 標準ではカメラ画像を外部送信しない。外部推論を検討する場合は別途承認する。

### MVPに含める
スキャン／カード訂正／日本語・英語検索／日本語名・本文・セット・使用可否／海外参考価格／版・言語・加工変更／次のスキャン／欠損・通信失敗・権限拒否時の案内。

### MVPに含めない
デッキ登録、所持数・状態・保管場所、コレクション総額、ログイン・同期、国内価格収集、売買、自動Foil判定、真贋判定、複数カード一括認識。閲覧履歴は後で優先度を判断する。

## 3. 技術構成（初期方針）

TypeScriptでドメインと接続インターフェースを定義し、Vitestで単体・契約・回帰テストを実行する。初期のUIはVite＋小さなTypeScript UIを候補とし、フレームワーク選定自体で認識検証を遅らせない。UI依存は初期シェル実装時に確定する。E2EはPlaywright候補。初期リポジトリにはまだ実カメラ・ライブ価格・モデルを接続しない。

```text
UI / Camera shell
  ├─ ScanSession / Selection（世代番号・手動選択・古い応答排除）
  ├─ RecognitionAdapter ─ Web Worker ─ 検出・補正・埋め込み・検索
  ├─ CardRepository ─ 日本語表示情報 / 印刷版カタログ
  ├─ PriceProvider ─ Scryfall USD / 対象版・市場の対応
  └─ FxProvider ─ USD/JPY / 基準日時
          ↓
   キャッシュ・必要な配信API（採用方式は技術検証後）
```

### 低レイテンシー設計
- UIの軽い初期シェルと重い認識モデル・カタログを分離する。初回ダウンロードはユーザー操作と重ねて体感の待ちを減らす一方、計測対象からは外さない。
- **Camera-first起動を第一候補とする（ユーザー提案）**。カメラを先に開き、カードを取り出して画角に合わせる操作とモデル・カタログのロードを重ね、体感の待ちを隠す。カメラ・認識・データ準備は並行開始し、全ロード完了までカメラを待たせない。
- 主に評価するのは「ユーザーがカードをかざしてから、正しい候補が出るまでの追加待ち」。初回全体・ロード完了・カード提示時刻も併記し、ロード時間とユーザー準備時間が重なった効果を計測する。容量だけを理由に採用を却下しない。
- ロードがカード提示に間に合わない場合だけ進捗を表示する。カメラ映像表示は認識readyと偽らず、端末性能・回線・すぐカードをかざすユーザーも別条件で試す。
- 推論はWorker候補。処理中フレームは原則1件、古いフレームをキューに溜めない。キャンセルと世代番号で古い結果を捨てる。
- 価格・為替のネットワーク待ちはカメラ開始・認識・メタデータ描画をブロックしない。
- 結果閲覧時は不要な推論を止める。背景移行時のカメラ解放・再開を実機で確認する。
- モデルとカタログはバージョン・互換性・ハッシュを含むmanifestで一組として管理。中断・更新失敗時は最後に正常な組へ戻す。
- ブラウザキャッシュ削除・容量不足・プライベートモードを考慮。キャッシュの永続性を保証しない。

### 情報の正しさ
- Oracleカード、実物の印刷版・言語・加工、日本語の表示情報、価格参照対象を分離する。
- 日本語印刷本文と最新Oracle本文を区別し、欠損を架空翻訳で補わない。
- USDと概算JPYを併記。「海外参考価格」であり国内販売・買取価格ではない。
- USD価格なしと0ドルを区別。JPY算出不可ならUSDだけ表示し、架空の固定為替を使わない。
- 為替基準日時、取得日時、価格の取得日時と供給元更新日時を混同しない。
- 手動版選択を推論結果で戻さない。版変更後は古い価格を消し、選択世代・対象が一致する価格応答のみ反映する。
- 他言語・別版の価格を参考表示する場合は代替であることと対象を明示する。黙って一致扱いしない。

## 4. エージェント分担と競合回避

| 担当 | 所有領域 | 責任 |
|---|---|---|
| LEAD（Hermes） | 共通契約、設定・lockfile、CI、計画、統合ブランチ | 優先度・承認・統合・最終Go/No-Go |
| VISION | `src/recognition/`, `tests/recognition/` | 認識方式比較、Worker、実画像と実機計測 |
| PRICE/DATA | `src/domain/pricing.ts`, `src/data/`, 対応単体テスト | 価格・為替・日本語データ・キャッシュ |
| STATE | `src/domain/selection.ts`, 対応単体テスト | 手動上書き・非同期競合防止 |
| UI | `src/ui/`, `tests/ui/` | カメラUI、日本語結果、版比較、操作・失敗案内 |
| TEST（独立） | `tests/regression/`, `tests/e2e/` | 契約・統合・回帰テスト、実装者の想定を独立検証 |
| QA（独立） | `docs/qa/`, 無視対象の証拠artifact | 探索テスト、表示・速度・端末差、公開可否報告 |

### 担当モデル
実装担当（PRICE/DATA・STATE・VISION実装・UI）はユーザー指定の **GPT-6.1-Sol (`gpt-6.1-sol`)** を各worker起動時に明示する。TEST/QAとLEADは独立させる。全体の既定モデルは変えず、指定モデルが使えなければ停止・報告し、黙って代替しない。

### Git worktree運用
1. LEADが共通契約と基準commitを確定。
2. **1エージェント＝1ブランチ＝1専用worktree**。同じcheckoutで同時編集しない。
3. worktreeごとに`npm ci`。node_modulesやテストartifactも共有しない。開発サーバーは担当ごとに別port。
4. `package.json`、`package-lock.json`、CI、共有型の変更はLEADだけ。依存追加・契約変更は提案→承認→基準commit更新の順。
5. エージェントは所有ファイルのみcommitし、SHA・変更ファイル・RED/GREEN実行結果・制約を返す。勝手にpush/mergeしない。
6. LEADが統合候補ブランチへ取り込み、TESTがその正確なSHAを専用worktreeで検証。
7. QAはTEST後の候補SHAを別worktreeで評価。実装者自身の「問題なし」だけで合格にしない。
8. 修正後は統合候補全体を再テスト。競合の自動強制解決・他担当の変更削除は禁止。
9. 初期bootstrap以降はPR単位で統合。GitHub保護ルールが契約プランで使えない場合は、その制約を報告し、LEADの手動ゲートで運用する。

worktreeは作業ファイルの衝突を防ぐだけ。設計・共有ファイルの競合は所有権と契約管理で防ぐ。エージェントはタスクごとに起動する独立コンテキストであり、常駐や無期限の自動進行を意味しない。同じGitHubアカウントを使うエージェントのレビューはGitHub上の別人承認とは数えない。

## 5. 開発フェーズと依存関係

以下の日数は順序を考えるための作業日目安であり、納期保証ではない。全体見積もりは認識・初回起動の検証後に改訂する。並列化しても実機計測と統合の待ち時間は消えない。

### P0：基盤・契約・独立検証の準備（初回セッション〜）
- private repo、計画、AGENTS、担当brief、worktree、TypeScript/Vitest/CIを整備。
- PRICEとSTATEが別worktreeで独立にTDD実装する。初期対象は純粋なUSD/JPY表示と手動選択・古い応答排除。
- TESTが独立回帰テスト、QAが初期実装・計画・未検証項目を確認。
- 出口：統合候補の型検査・テスト・GitHub CI通過、private確認、Obsidian計画保存。
- 注意：ここを完了してもスキャナーは未完成。モデル・実カメラ・価格供給元未接続を明示する。

### P1：実現性・速さの検証（目安3〜5作業日、ブロッカー次第で延長）
並行レーン：
- VISION：CollectorVision等の一次資料、コード・重み・カタログ・画像の条件、モデル容量、初期化時間、実機ランタイムを調査。採用許可を確認してから小規模実行。
- DATA：Scryfall価格の版・言語・加工対応、取得方針、日本語欠損、FX供給元・利用条件・キャッシュ方針を確認。
- UI：最小カメラシェルと認識準備状態、計測マーク、結果パネルを作る。試験用候補は明示し、本物の認識と混同しない。
- TEST/QA：実カード正解データと試験条件、初回/再訪/連続の計測手順を準備。
出口：最低1台で実画像を認識し、起動→認識→日本語情報→USD/JPY表示までの実測、ライセンス一覧、初回待ち時間を含む採否判断。
失敗時：まず検出・検索・転送・初期化のどこがボトルネックか切り分ける。モデル縮小、カタログ構造、OCR補助等を比較。ネイティブ化・外部画像送信は自動的に採用せずADRとユーザー判断へ。

### P2：MVPの縦通し（目安5〜10作業日）
P1で承認された契約・エンジンを基準として認識/UI/DATAを並行実装。
- スキャン→結果固定→日本語メタデータ・価格→版/言語/加工変更→次のスキャン。
- カード名訂正・日本語/英語検索、価格欠損、オフライン、権限拒否・復帰。
- 非同期取り違え、カメラ解放、キャッシュ更新・復旧の契約テスト。
出口：実データ経路で主要フロー完了。fixtureでの画面完成だけでは合格しない。

### P3：端末QA・限定利用（目安3〜5作業日＋協力者調整）
- iPhone Safari/PWA、Android Chromeの実機。具体的な端末・OSは機材確認後に固定。
- 日本語/英語、旧枠/特殊枠、同絵柄再録、Foil/スリーブ、両面等を正解付きで検証。
- 数枚を素早く調べる日常フローと、継続使用での発熱・遅延悪化の双方を測る。
- 協力者には価格の意味・版変更・再利用意向も確認。デッキ登録速度は評価対象外。
出口：QAの重大欠陥解消と性能ゲートを満たす対象端末だけを対応表に掲載。実機なしはNOT RUNとして公開判定を保留。

### P4：公開判断
ユーザー承認後に限定公開のURL・ホスティング・費用上限を決定。private repo作成はWeb公開の承認ではない。国内価格・コレクション・デッキはこの後の別判断。

## 7. 性能測定と暫定ゲート

ユーザー承認済みは「軽快さが必須」という方針。以下の数値は開発上の仮置きであり、達成実績でも承認済みSLOでもない。

| 指標 | 計測点 | 暫定目標／扱い |
|---|---|---|
| 再訪カメラ起動 | 起動操作→最初の利用可能フレーム | P50 1秒以内を仮目標 |
| 認識準備 | 起動→モデル・検索index初期化完了 | カメラ起動と別測定、P1で上限設定 |
| カード候補安定 | 定義した読取可能フレーム→正しい候補が安定 | P50 1秒以内を仮目標 |
| 情報・価格 | 候補安定→必要項目の実表示 | cache hitは同時に近く、missは別測定 |
| 初回全体 | キャッシュなし初回起動→最初の完全な結果 | 転送・展開・準備を含め全実測、P1で上限設定 |
| 尾の遅延 | 上記のP95・最大・失敗率 | 平均だけで合格にしない。P1で端末別上限設定 |

- 権限ダイアログの人間操作待ちは分離して報告し、アプリ待ちと混ぜない。ただし初回体験から消さない。
- 全計測にcommit、端末/OS/browser、通常/PWA、回線、cache状態、試行数、失敗数、モデル/catalog版、正解率を添える。
- 読取可能状態は試験動画の注釈など一定基準で定義。認識完了時刻から逆算して都合よく切らない。
- 初回/再訪/連続を混ぜた数字は禁止。小標本のP95は参考値として扱い、条件を明示する。
- 高速な誤認識は成功ではない。認識精度と版訂正時間を同時に見る。
- 基準を満たせない場合は黙って閾値を緩めず、原因・代替案・対応端末制限を相談する。

## 8. テスト・QAゲート

1. 実装者：単体TDD。外部通信・時計を分離し決定的なテストにする。
2. TEST：独立契約/回帰。古い価格応答、手動上書きと推論競合、next scan後の遅着結果、nullと0、FX不正、金額丸め・オーバーフロー。
3. UI統合：Playwright候補で版変更・誤認識訂正・欠損表示・アクセシビリティ・ネットワーク遅延を検証。合成フレーム/fixtureを明記。
4. QA：実データ・実カメラ・実端末で探索。desktop WebKitはiPhone Safari実機の代替証拠としない。
5. CI：`npm ci` → `npm run check`（型検査＋テスト）。UI開始時にbuild/E2E/アセットサイズ検査を追加。初期CIは実機性能を検証しない。
6. LEAD：修正後の統合SHA・CI・TEST/QAを確認。認識・表示の正しさと軽快さの両方が揃って初めて公開候補にする。

重大欠陥：別版の価格を一致として表示、手動選択の上書き、無断画像送信、再現性あるクラッシュ、許諾不明のモデル再配布。これらは公開ブロッカー。

## 9. リスクと保留事項

- CollectorVision等のコード/モデル/画像条件は個別確認。privateでもAGPL等への配慮は必要。採用・商用ライセンス購入は未決定。
- 初回モデル・カタログ容量が最大の性能リスク。認識精度だけで採用しない。
- Scryfallの価格対象と言語・加工の網羅性、画像利用条件、更新方針は一次ソースで確認。
- FX供給元、更新頻度、staleの許容時間はP1で決定。毎スキャン取得はしない。
- 端末機材、配信先、費用上限、初回/P95の確定閾値は未決定。
- 実カード画像・端末ログの収集は同意と保管方針を明示し、リポジトリへ無断投入しない。
- 短期の基盤完成やunit test成功はMVP完成ではない。作業結果は別の開始記録・QA報告に残す。
